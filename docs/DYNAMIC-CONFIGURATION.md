# Dynamic integration configuration

The Integrasi dashboard manages one Tebar profile/account pair and one OpenRouter model. The Tebar and OpenRouter API keys, webhook secret, database credentials, Telegram settings, sampling parameters, scheduler controls, and infrastructure settings remain server-side environment variables. The dashboard and configuration history never contain those secrets.

## Effective configuration and bootstrap

After migration `010_dynamic_configuration.sql`, the configuration service initializes `integration_config` once under MySQL row locks. For an existing installation it preserves a valid profile/account pair already stored in `settings`; otherwise it uses a complete valid pair from `TEBAR_PROFILE_ID` and `TEBAR_ACCOUNT_ID`. The initial model comes from `OPENROUTER_MODEL` or the existing application default. An incomplete initial configuration is persisted as `NOT_CONFIGURED`, and automation is disabled.

Once initialized, the MySQL row is authoritative. Subsequent app starts, `dispatch`, and `admin:create` read the row rather than replacing it with environment values. The initialization marker and configuration history distinguish a previously initialized installation from first startup; missing or malformed active configuration fails closed instead of silently falling back to `.env`. Database unavailability also prevents operations requiring configuration. `npm run migrate` applies schema but does not initialize the integration configuration by itself.

The configuration has a monotonically increasing version and append-only history. Authenticated update requests include the version displayed by the dashboard. A concurrent update returns `409 CONFIG_CONFLICT`; reload the Integrasi tab and repeat the validation using the newest values. Audit records contain the actor, operation, version, and safe validation result, not API keys or provider response bodies.

Integration and webhook HTTP requests receive a generated `X-Correlation-ID`; logs include the ID, route, method, status and authenticated actor where available. Each dispatcher run has its own correlation ID, with slot, session, configuration version and profile/account identifiers logged for claims and sends. Provider request bodies, credentials and captions are not logged by these events. Webhook deliveries are separate requests, so their correlation IDs are not automatically propagated from a prior dispatcher run; use the slot/provider identifiers and audit version to investigate across operations.

## Change an account

1. Open **Integrasi**, enter the Tebar profile ID and account ID, and validate the pair. Check the returned Threads username and status before confirming the change. Tebar must report that the account belongs to the profile, is active, is a Threads account, and is not plan-suspended.
2. Confirm the change in the dashboard. The backend verifies the pair again, pauses automation, cancels local `pending`, `generating`, and `ready` slots, and records the request. It does not transfer those slots to the new account.
3. If a slot is `publishing` or `unknown`, or a provider post is still `scheduled`/`draft`, the switch remains `BLOCKED_RECONCILIATION`. The pending target is visible while the previous pair remains active. Use **reconciliation** in Integrasi to retry provider checks and eligible cancellation; review the displayed outcome. Missing provider IDs and legacy slots without identity snapshots cannot be automatically reconciled.
4. When reconciliation is complete, validate the pending pair again and retry reconciliation. A successful activation leaves automation **off**. Review onboarding and the target account, then enable automation explicitly when appropriate. Enabling automation follows the existing scheduler's immediate-dispatch and cooldown behavior.

The account/profile pair changes atomically. All app instances use the database state; switching and publishing use MySQL row locks rather than an in-memory lock. A request already handed to Tebar can still finish after pause, and a timeout does not prove that publication failed. The app retains uncertain outcomes rather than replaying them blindly. Tebar documents an idempotency key for creating posts, but it is not an end-to-end exactly-once guarantee across every failure. See [Tebar Create a post](https://docs.tebar.app/reference/posts/create-post/) and [Tebar Webhooks](https://docs.tebar.app/en/api/webhook/).

New slots snapshot profile ID, account ID, and configuration version when created; model and model version are captured when generation begins. The exact outbound body and idempotency key are persisted before sending. Status checks and webhook matching use the slot's original account and profile, including after a change. Existing slots without an unambiguous profile/account snapshot are not assigned the current target automatically.

## Change a model or roll back

Use the searchable catalog in Integrasi, or enter an OpenRouter model ID manually. The backend queries OpenRouter metadata and checks text input/output and parameters required by the application, including `temperature` and `top_p` when configured. A successful metadata check does not guarantee future provider availability, account permissions, credit, or semantic-audit quality. If validation is unavailable or fails, the previous model remains active. See [OpenRouter model metadata](https://openrouter.ai/docs/api/api-reference/models/get-model).

The new model applies when the next generation starts. One snapshot is used for caption generation and its semantic audit; a ready slot and its saved payload are not regenerated. Provider failure uses the existing retry/failure handling; the semantic audit is not skipped and there is no silent model fallback.

History offers separate account and model rollback actions. Rollback validates the chosen component again and creates a new version instead of deleting history. Account rollback follows the same pause and reconciliation process and preserves the current model; model rollback preserves the current account pair. Rollback never revives canceled slots or retracts published posts.

## Recovery and deployment safeguards

- Stop or pause every **old-version** app, dispatcher, and scheduled CLI process before deploying this migration. Old binaries do not honor the new configuration fencing and can overwrite account fields from `.env`. Do not run mixed old/new worker versions during rollout or rollback.
- Back up MySQL before migration. MySQL DDL may implicitly commit: if migration `010` fails, leave workers stopped, inspect the migration ledger and actual table/column state, and restore a verified backup or rerun the migration only after investigating the failure. Do not delete history or manually mark a migration complete to bypass the failure.
- For `BLOCKED_RECONCILIATION`, retain automation off. Record the slot ID, original profile/account snapshot, provider post ID if present, and relevant timestamps. Check the post in the original Tebar profile and Threads account; a known provider ID can be retried through the dashboard. For a missing ID or legacy slot without a trustworthy profile snapshot, there is no built-in manual-resolution action and no safe automatic proof that an unacknowledged POST failed. Preserve the evidence and a database backup, keep the block, and escalate for a case-specific reviewed operator recovery; do not reset or reassign the slot to unblock publishing.
- If a publication conflicts with a previously recorded terminal status, the slot is marked `unknown` with `provider_status_conflict`. A late cancellation or failure response cannot silently clear the conflict. A confirmed published result can resolve it; other outcomes remain blocked for reviewed operator recovery.
- If the active configuration row is unavailable or corrupted, retain automation off and restore verified configuration/database state through a reviewed recovery procedure. Do not remove initialization markers or edit a slot's account to force a switch.
- Configuration rollback in the dashboard is distinct from image/database rollback. Restoring an old image can reintroduce `.env` overwrites; keep all workers stopped until compatibility with the restored database and configuration has been established. Restore the matching pre-deployment backup where required.

Staging verification remains required: use separate MySQL storage, Tebar workspace, Threads testing account, OpenRouter key, and Telegram destination. Verify profile access, model metadata, competing updates, pending/unknown recovery, delayed webhook handling, restart, and explicit reactivation. A live test post requires separate authorization and an isolated test account.
